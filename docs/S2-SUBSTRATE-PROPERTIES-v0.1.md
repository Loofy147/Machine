# S2 Substrate Properties v0.1

Recorded: 2026-09-19
Repository: Loofy147/Machine
Branch: research/substrate-interpreter-v0
Base experimental substrate: experiments/substrate-interpreter-v0.2/

## 1. Purpose

This document freezes the properties of S2 before any classification of S2 as an optimization, representation closure, or genuine substrate extension.

The target is the concrete experimental S2 implementation, not the canonical Machine substrate.

## 2. Definition

S2 is defined operationally as:

    S2 = S1 + direct indexed relation access

with:

    S1 = generic state read + comparison + branching + iteration
    S2 = S1 + relation_lookup_direct

The persistent relation representation is identical in the matched v0.2 experiment:

    state["rel"] : Mapping[key, value]

The S2 primitive is invoked as:

    relation_lookup_direct(state_read("rel"), key)

Therefore S2 does NOT bypass state access. It adds a distinct access operation after the relation value has already been read from machine state.

## 3. Properties

### P1 — Strict additive substrate contract

S2 adds exactly one exposed object-language primitive:

    relation_lookup_direct

No new state storage, control form, continuation form, closure representation, or language syntax is added.

Status: ESTABLISHED BY IMPLEMENTATION INSPECTION

Evidence:
- experiments/substrate-interpreter-v0.2/machine.py
- experiments/substrate-interpreter-v0.2/test_machine.py

### P2 — Same persistent information

The v0.2 control gives S1 and S2 the same relation object and the same stored entries.

No S2-specific reverse index or second representation is constructed by the interpreter.

Status: EXPERIMENTALLY_SUPPORTED

Scope:
- five-entry Python mapping
- five tested queries
- current experimental interpreter

### P3 — S2 preserves S1 behavior for S1 programs

An S1 program uses only the S1 primitive set. Because S2 only adds an additional global primitive and does not alter the semantics of existing primitives, tested S1 programs produce the same result and machine-state contents under both contracts.

Status: EXPERIMENTALLY_SUPPORTED

Boundary:
- tested programs only
- not a formal conservativity theorem for every possible program/value

### P4 — Direct lookup is read-only at machine-state level

The direct primitive performs a mapping lookup and increments access accounting. It does not write machine_data or mutate interpreter store in the current implementation.

Status: EXPERIMENTALLY_SUPPORTED

Boundary:
- ordinary dict-backed fixture
- host-level Mapping implementations with side effects are not excluded by the current type contract

### P5 — Lookup contract

For the current primitive:

- exactly two arguments are accepted;
- argument 0 must satisfy the host Mapping interface;
- argument 1 is the lookup key;
- an existing key returns its associated value;
- an absent key returns NIL;
- S1 rejects this primitive because it is not in the S1 contract.

Status: ESTABLISHED BY IMPLEMENTATION + TEST

Important boundary:
"Mapping" is a host-language interface. The present contract does not define an independent object-language relation type.

### P6 — Access cost is explicit

Each successful invocation of relation_lookup_direct charges:

    +1 access tick

The complete benchmark also charges state_read separately.

Therefore direct lookup is not represented as zero-cost access in the current accounting.

For a direct query:

    access_ticks = state_read cost + direct lookup cost

Status: ESTABLISHED BY IMPLEMENTATION + TEST

### P7 — No hidden preprocessing inside S2

The S2 primitive does not construct a reverse index, cache, or target-specific table at lookup time.

The experiment therefore compares access mechanisms over an already available representation.

Status: ESTABLISHED BY IMPLEMENTATION INSPECTION

Boundary:
The benchmark's reported offline construction cost is supplied by the experiment harness; it is not generated by relation_lookup_direct itself.

### P8 — Semantic equivalence on the tested relation workload

For the five-entry mapping and five online queries:

    S1 results = S2 results
                = [40, 0, 20, NIL, 30]

This supports semantic equivalence on the tested finite workload.

Status: EXPERIMENTALLY_SUPPORTED

It does not establish universal equivalence over arbitrary hosts, values, mappings, or programs.

### P9 — S2 adds access, not information availability

Because the S2 expression first evaluates:

    state_read("rel")

the direct primitive does not make the relation exist earlier, reveal hidden state, or bypass the timing of state availability.

Its changed capability is how an already-readable relation value may be accessed.

Status: ESTABLISHED FOR THE EXPERIMENTAL CONTRACT

### P10 — No complexity theorem from one access tick

The implementation charges one abstract access tick to direct lookup. This is an accounting rule, not an asymptotic complexity proof.

The underlying host Mapping may have implementation-dependent lookup cost.

Status: UNKNOWN / NOT CLAIMED

Therefore the experiment supports a measured resource advantage under the declared cost model, not a general O(1) theorem.

### P11 — Direct primitive is host-semantics dependent

The implementation checks isinstance(x, Mapping) and invokes x.get(key, NIL).

Thus S2 currently depends on host-language Mapping semantics.

A custom Mapping implementation could have behavior outside the abstract relation contract.

Status: SPECIFICATION DEBT

This must be resolved before treating S2 as a closed language-level primitive.

### P12 — S2 is not proven to enlarge absolute computability

The current evidence shows a large measured resource difference while reproducing the same observed results.

It does not prove that all computations expressible with S2 are expressible with S1 under every resource bound, nor that S2 can never enlarge an admissible task set under a different budget contract.

Status: OPEN

## 5. Consequence for the frontier question

The strongest currently justified statement is:

> S2 is an additive access mechanism over an already available relation representation. In the matched v0.2 experiment it preserves observed semantics while substantially reducing measured online work. The evidence therefore establishes a resource-access distinction, but not an absolute computational-capability separation.

A stronger classification requires resolving the host-Mapping boundary and reproducing these properties on the canonical Machine substrate.

## 6. Required next tests

1. Replace the host-dependent Mapping contract with an explicitly specified object-language relation representation, or explicitly declare host Mapping semantics part of the substrate.
2. Test S2 over generated mappings, including hits, misses, NIL-valued entries, repeated queries, and multiple value types.
3. Measure the full cost vector:

       (B_off, R, B_on, C_access)

4. Repeat the same property suite on the canonical Machine interpreter once its concrete substrate is identified.

## 7. Validity boundary

These properties describe the experimental S2 implementation at the recorded branch/ref. They must not be propagated to the canonical Machine substrate without a source-level reconciliation.
